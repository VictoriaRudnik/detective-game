# Detective Game with Live Suspects — Design

Date: 2026-10-08
Status: Approved in brainstorming, pending spec review

## 1. Goal and context

A browser murder-mystery game. Players interrogate suspects; each suspect is an LLM (Claude) driven by a hidden prompt containing their personality, alibi and secret. The goal is to identify the killer.

- **Purpose:** pet project for learning the LLM API (structured outputs, streaming, prompt design, caching), with clean architecture and code. Played with friends; may grow into a public game.
- **Cases:** a new case is generated by the LLM for every game.
- **Modes:** solo, or co-op — the host shares a link, everyone joins one shared real-time investigation. Solo is a room with one player.
- **Languages:** English and Russian. The host picks the language when creating the room; the case and all suspect answers are in that language.

## 2. Game rules

- **Lobby:** host picks language (en/ru) and suspect count (3–5), creates a room. Friends join via link and enter a name. Host presses Start → case is generated.
- **Moves:** a shared budget per room, `moves = 3 × suspectCount + 3` (3 suspects → 12, 4 → 15, 5 → 18). One move = one question to one suspect.
- **Turns:** round-robin over connected players. Only the active player can ask. Everyone can write in the room chat at any time; chat costs no moves and is never sent to the LLM.
- **Briefing:** at the start everyone sees victim, location, time of death, cause of death, setting, and the public descriptions of the suspects. Further facts come only from interrogation. The game does not track clues.
- **Accusation:** any player may propose a vote while investigating (and no answer is streaming). Every connected player votes for one suspect. A strict plurality winner → reveal. A tie → back to investigating with a system message.
- **Forced vote:** when `movesLeft` reaches 0 the room enters a forced vote. On a tie in a forced vote, the accused is chosen randomly among the tied suspects.
- **Ending:** the reveal shows whether the room was right, plus the killer, method, motive, key evidence and every suspect's secret and true alibi.
- **Persistence:** rooms live in server memory only. A server restart loses games. Acceptable for the MVP.

## 3. Architecture

pnpm-workspaces monorepo, TypeScript everywhere.

```
game/
├─ packages/shared/            types + zod schemas shared by client and server
│   ├─ case.ts                 Case, Suspect, Solution
│   ├─ room.ts                 RoomState, PublicRoomView, Player, Phase, Vote, LogEntry
│   └─ events.ts               Socket.IO event contracts (zod)
├─ apps/server/                Node + Fastify + Socket.IO
│   ├─ engine/reducer.ts       pure game logic: (RoomState, Action) → RoomState | GameError
│   ├─ engine/publicView.ts    RoomState → PublicRoomView (strips hidden data)
│   ├─ llm/CaseGenerator.ts    interface + ClaudeCaseGenerator
│   ├─ llm/SuspectResponder.ts interface + ClaudeSuspectResponder
│   ├─ llm/caseValidator.ts    pure consistency checks
│   ├─ llm/prompts/            prompt templates (en, ru)
│   ├─ llm/fakes.ts            FakeCaseGenerator, FakeSuspectResponder (tests, dev)
│   ├─ rooms/RoomManager.ts    in-memory rooms, applies actions, orchestrates LLM calls
│   ├─ transport/socket.ts     Socket.IO ↔ RoomManager, zod validation of events
│   └─ scripts/genCase.ts      `pnpm gen:case` — generate and print a real case
└─ apps/client/                React + Vite
    ├─ i18n/                   en.json, ru.json (react-i18next)
    ├─ net/useRoom.ts          Socket.IO hook exposing PublicRoomView + actions
    └─ screens/                Home, Lobby, Generating, Investigation, Vote, Reveal
```

**Boundaries**
- `engine` has no I/O: no network, no LLM, no timers, no randomness (randomness is injected). Fully unit-testable.
- `llm` is the only module importing `@anthropic-ai/sdk`. Everything else depends on the `CaseGenerator` / `SuspectResponder` interfaces.
- `RoomManager` wires engine + LLM + broadcasting. `transport` only translates socket events to RoomManager calls.
- Hidden case data (persona, alibi, secret, knows, isKiller, solution) never leaves the server before `revealed`. Enforced by `publicView.ts` and covered by tests.

## 4. Claude integration

- SDK: `@anthropic-ai/sdk`. API key in `ANTHROPIC_API_KEY`, server-only, loaded from `.env` (gitignored).
- Models via env: `CASE_MODEL` and `SUSPECT_MODEL`, both defaulting to `claude-opus-5-5`.
- **Case generation:** one streamed request, adaptive thinking, `output_config.effort: "high"`, structured output via `output_config.format` with a JSON schema derived from the zod `Case` schema (excluding server-assigned fields such as `id`). Parsed with zod, then validated (§5).
- **Suspect answers:** streamed, `output_config.effort: "low"`. System prompt = shared case facts + the suspect's persona, claimed/true alibi, secret, knows, and behavior rules (stay in character, never reveal being an AI, lie about the secret unless cornered, the killer protects themselves but may slip under strong pressure, answer in the room language, keep answers short — 2–5 sentences). The system prompt is static per suspect and marked with `cache_control` so repeated questions hit the prompt cache.
- **Memory:** each suspect keeps its own message history (`MessageParam[]`) — only the questions addressed to them and their answers. The history is append-only.
- **Refusals:** check `stop_reason` before reading content; a `refusal` is treated as an LLM failure (§7).
- Exact SDK calls are confirmed against the claude-api skill docs during implementation, not from memory.

## 5. Case model, generation and validation

```ts
Case {
  id: string
  language: 'en' | 'ru'
  title: string
  briefing: { victim; location; timeOfDeath; causeOfDeath; setting }   // public
  suspects: Suspect[]                                                  // 3–5
  solution: { killerId; method; motive; keyEvidence: string[] }        // hidden
}
Suspect {
  id; name; role; publicDescription                                     // public
  persona: { personality; speechStyle }                                 // hidden
  alibi: { claimed; truth }                                             // hidden
  secret: string                                                        // hidden, every suspect has one
  knows: string[]                                                       // hidden facts they can reveal
  isKiller: boolean                                                     // hidden
}
```

**Generation is solution-first:** the prompt tells the model to decide the truth (killer, method, motive, timeline) before writing the suspects, and requires: every suspect has a secret (innocents' secrets are red herrings); the killer's claimed alibi differs from the truth; key evidence is distributed across the non-killers' `knows`.

**Validator (pure function, returns a list of errors):**
- exactly one suspect with `isKiller`, and its id equals `solution.killerId`;
- suspect count equals the requested count; ids unique;
- killer's `alibi.claimed !== alibi.truth`;
- `keyEvidence` non-empty, and each item appears in at least one non-killer's `knows` (the model is told to copy the evidence strings verbatim; comparison is case-insensitive after trimming);
- `case.language` equals the requested language;
- all text fields non-empty.

**Retry:** on parse or validation failure, retry with the error list appended to the prompt, up to 2 retries (3 attempts total). On final failure the room returns to `lobby` with an error message.

## 6. Room state, phases, events

**Phases:** `lobby → generating → investigating ⇄ voting → revealed`; `generating → lobby` on failure; `revealed → lobby` on "New game" (host).

```ts
RoomState {
  id                          // 6 chars, uppercase letters+digits, no ambiguous chars
  hostId; language; suspectCount
  players: { id; name; connected }[]
  phase: Phase
  case?: Case
  movesLeft: number
  turnPlayerId?: string
  log: LogEntry[]             // {id, kind: 'question'|'answer'|'chat'|'system', playerId?, suspectId?, text, ts}
  suspectHistories: Record<suspectId, MessageParam[]>
  vote?: { initiatorId; ballots: Record<playerId, suspectId>; forced: boolean }
  pendingAnswer?: { suspectId; entryId }
  result?: { accusedId; correct: boolean }
}
```

`PublicRoomView` contains the same minus `suspectHistories`, with `case` reduced to `{title, language, briefing, suspects: {id, name, role, publicDescription}[]}` until `revealed`, when the full case is included.

**Client → server:** `room:create {name, language, suspectCount}`, `room:join {roomId, name, playerId?}`, `game:start`, `ask {suspectId, text}`, `chat {text}`, `vote:propose`, `vote:cast {suspectId}`, `game:restart`.
**Server → client:** `room:state PublicRoomView`, `answer:delta {entryId, text}`, `error {code, message}`, and acks on `room:create`/`room:join` returning `{roomId, playerId}`.

**Ask flow:**
1. Reducer validates: phase `investigating`, sender is `turnPlayerId`, `movesLeft > 0`, no `pendingAnswer`, suspect exists, text 1–500 chars.
2. Append question entry and empty answer entry, `movesLeft -= 1`, set `pendingAnswer`, broadcast.
3. RoomManager streams `SuspectResponder` output as `answer:delta`.
4. On completion: fill answer entry, append Q/A to that suspect's history, clear `pendingAnswer`, advance turn to next connected player; if `movesLeft === 0`, enter forced vote. Broadcast.

**Vote flow:** `vote:propose` allowed in `investigating` without `pendingAnswer`. Vote resolves when all connected players have cast a ballot (a disconnect during voting re-checks resolution). Resolution per §2.

**Connections:** `playerId` stored in `localStorage`; rejoining with a known `playerId` restores the player. Disconnected players are skipped in turn order; if the active player disconnects, the turn advances. If the host disconnects, the next connected player becomes host. A room with no connected players is deleted after 30 minutes. Joining is allowed in any phase (late joiners enter the turn rotation).

## 7. Error handling

- Every incoming socket payload is validated with zod; invalid → `error` event, state unchanged.
- Reducer returns typed `GameError {code}` (e.g. `NOT_YOUR_TURN`, `NO_MOVES_LEFT`, `ANSWER_IN_PROGRESS`, `WRONG_PHASE`, `NOT_HOST`); client shows an i18n toast keyed by code.
- Suspect answer fails (API error after SDK retries, refusal, empty answer): remove the empty answer entry, refund the move, add a system entry ("The suspect stays silent… try again"), keep the turn with the same player, do not touch the suspect's history.
- Case generation fails after retries: phase back to `lobby`, `error` event with code `CASE_GENERATION_FAILED`.
- The SDK's built-in retries handle 429/5xx; no custom retry layer.

## 8. Client

- **Home:** name, language (EN/RU), suspect count (3–5), "Create game"; or enter a room code to join. Visiting `/room/:id` goes straight to the name prompt + join.
- **Lobby:** room code, "Copy link", player list, Start (host only).
- **Generating:** waiting screen.
- **Investigation:** briefing + suspect cards (left), shared log with live-streaming answers (center), question input only for the active player with "Waiting for <name>…" otherwise, room chat, moves counter and "Accuse" button.
- **Vote:** suspect cards, own ballot, who has voted.
- **Reveal:** correct/incorrect, killer, method, motive, key evidence, each suspect's secret and true alibi, "New game" (host).
- i18n via react-i18next, `en.json` + `ru.json`; UI language defaults to the room language with a manual switcher.
- Visual style: atmospheric noir, decided during implementation.

## 9. Testing

- Vitest across the monorepo.
- `engine/reducer`: every action × phase, turn rotation with disconnects, move budget, forced vote, ties, host transfer.
- `publicView`: hidden fields absent before `revealed`, present after.
- `caseValidator`: one valid case plus one failing case per rule.
- `RoomManager` + Socket.IO integration test with fake LLMs and real socket clients: create → join → start → ask → stream → vote → reveal; LLM failure refunds the move; generation failure returns to lobby.
- No automated tests against the real API. `pnpm gen:case [--lang ru] [--suspects 4]` prints a real generated case for manual review.
- A few client component tests for key screens.

## 10. Out of scope (MVP)

Accounts, database/Redis persistence, a second LLM pass that reviews case solvability, scoring and leaderboards, deployment and hosting, rate limiting/abuse protection for public use, spectator mode.
